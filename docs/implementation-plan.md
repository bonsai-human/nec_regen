## 1. ゲーム概要

六角形のマスで構成されたマップ上で、2つの陣営が交互にユニットを動かして戦う
ターン制の戦術シミュレーション。原作の面白さの核である

- **サポート（囲む）補正** — 敵を複数ユニットで囲むほど攻撃が強くなる
- **工場占領による増援** — 中立/敵の工場を奪うと補充ユニットが供給される
- **ZOC** — 敵の隣に踏み込むとそこで移動終了。戦線が意味を持つ
- **地形** — 移動コストと防御力が地形とユニット種別で変わる

を維持しつつ、舞台を宇宙から**現代の地球**へ移し、**海上戦力と沿岸戦**を新しい戦術軸
として追加する。

### 原作からの主な変更点

| 観点 | 原作 | 本作 |
| --- | --- | --- |
| 舞台 | 月面・宇宙 | 現代地球（沿岸部を含む） |
| 地形 | 陸上中心 | 海洋・浅瀬・港・砂浜を追加 |
| ユニット | 陸・空中心 | 陸・空に加えて艦艇・潜水艦・揚陸を追加 |
| 輸送 | 限定的 | 輸送ヘリ/揚陸艦による積載・揚陸を戦術要素として設計 |

## 3. アーキテクチャ

### 3.1 レイヤ構成

```
src/
├── core/          ゲームロジック（純粋・DOM 非依存・テスト対象の中心）
│   ├── hex.ts             ヘクス座標系と幾何計算
│   ├── types.ts           GameState / Unit / Tile などの型定義
│   ├── map.ts             マップ生成・タイル参照
│   ├── movement.ts        移動コスト・到達範囲・経路探索（ZOC 込み）
│   ├── combat.ts          戦闘計算（サポート補正・反撃）
│   ├── capture.ts         施設占領・増援
│   ├── victory.ts         勝敗判定
│   ├── commands.ts        コマンド定義と検証
│   └── reducer.ts         reduce(state, command) => { state, events }
├── ai/            CPU 思考（core にのみ依存）
│   ├── types.ts           AI インターフェース
│   ├── greedy.ts          v1: 貪欲AI
│   └── evaluator.ts       v2: 評価関数型AI
├── render/        Canvas 描画（core を読むだけ。state を書き換えない）
├── ui/            入力処理・画面遷移・パネル・アニメーション制御
├── data/          JSON ローダとスキーマ検証
├── editor/        マップエディタ（別エントリポイント）
└── main.ts

data/
├── units.json      ユニット性能表
├── terrain.json    地形定義
└── maps/*.json     マップデータ
```

**依存の向き**: `ui → render → core`、`ui → ai → core`。core は他を一切参照しない。
この分離により、core だけをヘッドレスで走らせて AI 同士の自動対戦テストが行える。

### 3.2 状態更新モデル（コマンドパターン）

すべてのプレイヤー操作・AI 操作を **Command** として表現し、単一の reducer で状態を更新する。

```ts
type Command =
  | { type: 'move';    unitId: UnitId; path: Hex[] }
  | { type: 'attack';  unitId: UnitId; targetId: UnitId }
  | { type: 'capture'; unitId: UnitId }
  | { type: 'wait';    unitId: UnitId }
  | { type: 'endTurn' };

function reduce(state: GameState, cmd: Command): { state: GameState; events: GameEvent[] };
```

`events`（`unitMoved` / `unitDamaged` / `unitDestroyed` / `facilityCaptured` …）は描画・
アニメーション・効果音のトリガとして使い、core は描画を知らない。

この設計により以下が自然に得られる。

- **アンドゥ**: 状態のスナップショット、またはコマンド列の再生
- **リプレイ**: 乱数なし・決定的なので「初期状態 + コマンド列」で完全再現
- **AI の先読み**: AI が仮想的に reduce を回して手を評価できる
- **セーブ/ロード**: GameState を JSON 化して localStorage へ
- **将来のオンライン対戦**: コマンドを送受信すればよい形になっている

## 4. ゲームルール仕様

> 本章の数値はすべて JSON の定数として外に出し、コード変更なしで調整できるようにする。
> 「原作準拠」と書いた箇所も、実プレイでの検証を経て第9章のバランス調整フェーズで確定させる。

### 4.1 座標系

- **フラットトップ（左右に頂点、上下が平ら）のヘクス**を、列ごとに縦方向へずらして配置。
  近隣は N / S / NE / SE / NW / SW の6方向。
- **保存形式**: マップ JSON は人間が読める `odd-q` オフセット座標（列・行の二次元配列）。
- **内部計算**: 読み込み直後に軸座標 (q, r) へ変換。距離・近隣・範囲計算はキューブ座標で行う。

```
軸座標への変換: q = col,  r = row - (col - (col & 1)) / 2
距離: (|dq| + |dq + dr| + |dr|) / 2
```

### 4.2 ターン進行

1. **ターン開始フェーズ**
   - 占領済み工場からの増援を出現させる
   - 港・飛行場・司令部の隣接/在マスにいる自軍ユニットを補給・修理（オプション、既定OFF）
   - 全ユニットの行動済みフラグをリセット
2. **操作フェーズ** — ユニットごとに「移動 → 攻撃 / 占領 / 待機」を1回ずつ実行
3. **ターン終了** — 勝敗判定 → 相手プレイヤーへ

ユニットは1ターンに **移動1回 ＋ 行動1回**。攻撃・占領を行うと行動終了。
移動せずにその場で攻撃することも可能。

### 4.3 移動

- ユニットは **移動力（MP）** を持ち、進入するヘクスの移動コストを支払う
- コストは **地形 × 移動タイプ** の表で決まる（`terrain.json`）
- 移動タイプ: `foot`（歩兵） / `wheel`（装輪） / `track`（装軌） / `hover` / `air` / `ship`（水上） / `sub`（潜水）
- 進入不可の組み合わせはコスト `null`（例: 戦車と外洋、艦艇と平地）
- 経路探索は移動コスト付きダイクストラ。到達可能ヘクスをハイライト表示
- 味方ユニットのいるヘクスは**通過可能・停止不可**。敵ユニットのいるヘクスは通過不可
- **ZOC**: 敵ユニットに隣接するヘクスへ進入した時点で移動終了。
  - 開始位置が既に ZOC 内の場合、そこから1ヘクスだけは移動できる（膠着を避けるため）
  - 航空ユニットは ZOC の影響を受けない（原作準拠）
  - ZOC を発生させるのは地上/海上ユニットのみ

### 4.4 戦闘（戦力10制・決定的）

各ユニットは **戦力 S**（初期値 10、0 で撃破）を持つ。戦力は攻撃力・被ダメージ量の両方に効く。
**乱数は使わない**ため、ダメージ予測を UI に常時表示でき、AI も正確に読める。

#### ダメージ計算

```
supportMul(n) = 1 + SUPPORT_STEP × min(n, SUPPORT_CAP)        // 既定: 0.15, 4

attackerMod = (S_attacker / 10) × supportMul(n_attacker)
defenderMod = DEF[defender.type]
              × terrainDefense[defender.tile][defender.type]
              × supportMul(n_defender)

damage = clamp( round( ATK[attacker.type][defender.armorClass]
                       × attackerMod / defenderMod ),
                0, S_defender )
```

- `ATK` は「攻撃側ユニット種別 × 防御側の耐性クラス（歩兵 / 装甲 / 艦艇 / 航空 / 潜水）」の表
- `DEF` はユニット固有の防御係数
- `terrainDefense` は地形の防御補正（市街・森・山でユニット種別ごとに変化）

#### サポート補正（本作の核）

- `n_attacker` = **防御側ユニットに隣接している攻撃側ユニットの数**（攻撃を実行したユニット自身は除く）
- `n_defender` = **攻撃側ユニットに隣接している防御側ユニットの数**（防御ユニット自身は除く）

つまり「敵を囲むほど強く殴れる／自分が囲まれているほど弱い攻撃になる」。
戦線を維持し、突出した敵を包囲する動きが最善手になる。

> ⚠️ 原作の正確な係数は資料により差異があるため、`SUPPORT_STEP` / `SUPPORT_CAP` は
> 調整パラメータとして扱い、プレイテストで決定する。

#### 反撃

- 攻撃解決後、防御側の戦力が 1 以上で、かつ攻撃側が**反撃可能な射程内**にいる場合、
  同じ式で反撃が発生する（このとき攻守の役割とサポート計算は入れ替わる）
- **間接攻撃ユニット**（自走砲・MLRS・ミサイル艦）は
  - 移動後に攻撃できない
  - 射程 2〜3 から攻撃し、反撃を受けない
  - 隣接した敵には攻撃できない（原作の間接砲と同じ扱い）
- **対空ユニット**は航空機に大ダメージ、地上目標には低ダメージ
- **潜水艦**は対潜能力を持つユニットからのみ攻撃を受ける

### 4.5 施設と増援

| 施設 | 効果 |
| --- | --- |
| 司令部（HQ） | 陣営の本拠地。占領されると敗北 |
| 工場 | 占領すると増援ユニットを供給。地上ユニットの補給・修理点 |
| 港 | 艦艇の補給・修理。海上ユニット増援の出現点 |
| 飛行場 | 航空ユニットの補給・修理・増援出現点 |

- 占領は**地上ユニット（歩兵系）のみ**が実行できる。施設ヘクスに乗り、`capture` を実行
- 占領は1ターンで完了（原作準拠。段階制にする案は後述の検討課題）
- **増援**: 各施設はマップ JSON に「出現ユニット列（キュー）」と「出現間隔」を持つ。
  占領している陣営が、間隔ターンごとにキューの先頭を隣接空きヘクスへ出現させる。
  キューが尽きたらそれ以上は出ない（資源管理ではなく、マップ設計で戦力配分を制御する方式）

### 4.6 輸送・積載（海洋要素の中核）

- **輸送ヘリ / 輸送トラック / 揚陸艦** は積載枠を持つ
- 積載可能なのは歩兵系ユニット（揚陸艦は車両も可）
- 積載中のユニットは行動できず、輸送ユニットが撃破されると同時に失われる
- **揚陸**: 揚陸艦は「砂浜」「港」に隣接した浅瀬から、地上ユニットを陸上ヘクスへ降ろせる
- 降ろされたユニットはそのターン行動済み（強襲上陸を強すぎなくするため）

これにより「海側から迂回して手薄な工場を奪う」「対艦ミサイルで揚陸部隊を沈める」といった
原作にはなかった読み合いが生まれる。

### 4.7 勝敗条件

以下のいずれかで決着。マップ JSON でどれを有効にするか指定する。

1. 敵ユニットの全滅
2. 敵司令部の占領
3. 規定ターン経過時点での判定（残存戦力・占領施設数で比較）

## 6. AI 設計

`ai/types.ts` にインターフェースを切り、実装を差し替えられるようにする。

```ts
interface AiPlayer {
  planTurn(state: GameState, playerId: PlayerId): Command[];
}
```

### v1（MVP 用・貪欲）

各ユニットについて、実行可能な行動を列挙し、単純なスコアで最良手を選ぶ。

1. 攻撃可能な敵がいれば、`与ダメージ − 想定反撃ダメージ` が最大の攻撃を選ぶ
2. 占領可能な施設に乗れるなら占領
3. どちらもなければ、最も近い敵または未占領施設へ向かって前進

これだけでも ZOC とサポートがあるため「ある程度戦っている」ように見える。

### v2（評価関数型）

盤面評価関数を定義し、1ターン分の行動順を貪欲＋局所探索で最適化する。

```
score = Σ(自軍ユニット戦力 × 種別価値) − Σ(敵軍同)
      + W_facility × 占領施設数の差
      + W_hq       × 敵HQへの距離の逆数
      + W_support  × サポート優位（自軍が敵を囲めている数 − その逆）
      + W_terrain  × 各ユニットの地形防御ボーナス
```

- 行動順序（誰から動かすか）が結果を大きく変えるため、
  複数の順序をサンプリングして最良のものを採る
- 相手の反撃は1手先まで読む（`reduce` を仮想実行してシミュレート）
- 難易度は、評価関数の重みと「あえて最善を選ばない確率」で3段階を用意

### 自己対戦テスト

ヘッドレスで AI 同士を数百戦させ、
- 例外・無限ループ・不正コマンドの検出
- マップごとの先手勝率（バランス指標）
を CI とは別のスクリプトで測定する。

## 7. UI / UX

### 画面

1. **タイトル** — マップ選択、難易度選択、続きから
2. **メインゲーム** — ヘクスマップ + 情報パネル
3. **リザルト** — 勝敗、ターン数、損害集計

### 操作（マウス主体、キーボード補助）

| 操作 | 挙動 |
| --- | --- |
| ユニットをクリック | 選択。到達範囲を青、攻撃可能範囲を赤でハイライト |
| 移動先をクリック | 経路をプレビュー表示 → 確定で移動 → 行動メニュー（攻撃/占領/待機） |
| 敵ユニットにホバー | **ダメージ予測を表示**（乱数なしなので確定値。与ダメージと反撃ダメージの両方） |
| 右クリック / Esc | 選択解除・1手戻る |
| ホバー | 地形とユニットの詳細をパネルに表示（サポート数も明示） |
| `U` | アンドゥ（そのターン内の自分の行動のみ） |
| `Space` | 未行動ユニットへ順にジャンプ |
| `Enter` | ターン終了（未行動ユニットがあれば確認） |

**サポート数の可視化**は本作の学習コストを大きく下げるので優先度を高くする。
選択中ユニットが敵を攻撃する際、サポートに寄与している味方ヘクスを枠線で示す。

### 描画

- Canvas をレイヤ分割: 地形（オフスクリーンにキャッシュ）→ グリッド → ハイライト → ユニット → エフェクト → HUD
- 地形は静的なので初回のみ描画してキャッシュ。毎フレーム描くのはユニット以上のレイヤのみ
- アニメーション（移動・被弾・撃破）は `events` を消費するキューで処理し、
  再生中は入力をブロックする。**スキップ設定**を必ず用意する（AI ターンが長いとストレスになる）
- ユニット表現は Phase 2 までは色付きヘクス＋記号のプレースホルダ。Phase 6 以降で自作スプライトに差し替え

## 8. マップエディタ

`editor.html` を別エントリポイントとして用意（本編とコードを共有）。

- 地形パレットからのブラシ塗り、矩形塗り
- ユニット・施設の配置と所属陣営の切り替え
- 施設の増援キュー編集
- 検証（HQ が両陣営に存在するか、孤立した施設がないか、初期戦力の均衡）
- **JSON のエクスポート / インポート**（ファイル保存 + クリップボード）
- 「このマップをテストプレイ」ボタンで本編を起動

| 3 | 戦闘 | 攻撃可能判定、サポート数計算、ダメージ計算、反撃、間接攻撃、撃破処理、ダメージ予測表示 | 戦闘計算のゴールデンテスト（想定ケース表）が全通過 |

| 6 | UI 仕上げ | タイトル画面、情報パネル、サポート可視化、アニメーションとスキップ、自作スプライト・効果音 | 初見でもルールを理解して遊べる |

## 10. テスト戦略

| 種別 | 対象 | 方針 |
| --- | --- | --- |
| 単体テスト | `core/` 全体 | ヘクス幾何、移動コスト、ZOC、戦闘計算、占領、勝敗判定。core は純粋関数なので網羅しやすい |
| ゴールデンテスト | 戦闘計算 | 「攻撃側/防御側/地形/サポート数 → 期待ダメージ」の表をテストデータ化。バランス調整時の意図しない変化を検出 |
| シナリオテスト | reducer | 決まったコマンド列を流し、最終状態を検証（リプレイ機構をそのままテストに使う） |
| 自己対戦 | AI + core | 数百戦を回して例外・無限ループ・膠着を検出 |
| 手動確認 | UI | フェーズごとにチェックリストで確認 |

CI では `typecheck` → `lint` → `test` → `build` を実行する。

## 11. 権利・法務上の注意

- 原作の**名称・ロゴ・キャラクター・マップ・グラフィック・音楽・効果音は一切使用しない**
- ユニット名・地形名は一般名詞（「主力戦車」「森林」など）を使う
- 素材は自作、または CC0 / パブリックドメインのもののみ。使用素材はライセンスを
  `docs/CREDITS.md` に記録する
- 公開時の説明文でも原作タイトルを冠さない（「ヘクス戦術シミュレーション」等で表現する）
- ルール・システムのアイデア自体は著作権保護の対象外だが、上記により表現面での問題を回避する

## 12. 検討課題（レビューで決めたい点）

実装前に方針を確定したい項目。**太字が本書としての推奨案**。

1. **占領の所要ターン** — **1ターンで完了（原作準拠、テンポ重視）** / 2ターン制（防衛の余地が生まれる）
2. **補給・修理** — **既定 OFF（原作にない要素のため）**。港・飛行場に置いた艦載機/艦艇の
   運用が苦しければマップ単位のオプションとして ON にできる形にする
3. **サポート補正の係数** — 推奨は `+15% × min(隣接数, 4)`（最大 +60%）。
   原作の体感に近づくよう Phase 4 のプレイテストで調整
4. **索敵（Fog of War）** — **既定 OFF**（原作は全面可視）。潜水艦のみ「対潜ユニットに
   隣接していないと攻撃対象にできない」という限定的な隠匿で海の駆け引きを表現する
5. **航空ユニットの燃料** — **なし**（原作準拠）。無制限に飛べる代わりに、対空ユニットを
   強めに設定して抑止する
6. **マップサイズ** — 初期マップは 20×14 前後を想定。エディタで自由に変更可能
7. **陣営数** — **2陣営固定**。3陣営以上はデータ構造上は許容するが UI/AI では対応しない

## 13. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 数値バランスが煮詰まらない | ゲームとして面白くならない | 全定数を JSON 化。Phase 4 でプレイテスト期間を明示的に確保。自己対戦で定量評価 |
| サポート/ZOC がプレイヤーに伝わらない | 戦術が理解されず作業ゲーに見える | サポート数の可視化とダメージ予測を Phase 3 の必須項目に含める |
| AI ターンが長い / 見ていて退屈 | 体験の質が落ちる | 探索の深さに上限を設ける。アニメーション速度設定とスキップを必ず用意 |
| ユニット21種の作り込みで停滞 | MVP が遠のく | Phase 4 までは 8種程度で進め、システム確定後に JSON で追加する |
| 海洋要素が陸戦と噛み合わない | 追加要素が死ぬ | Phase 8 で沿岸マップを専用設計し、「海路が最短の目標」を必ず配置する |
| 素材制作がボトルネック | 見た目が最後まで仮のまま | Phase 6 まではプレースホルダ図形で進行。ロジック完成を優先 |
