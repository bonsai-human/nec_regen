## 1. ゲーム概要

六角形のマスで構成されたマップ上で、2つの陣営が交互にユニットを動かして戦う
ターン制の戦術シミュレーション。原作の面白さの核である

- **サポート（囲む）補正** — 敵を複数ユニットで囲むほど攻撃が強くなる
- **工場占領による増援** — 中立/敵の工場を奪うと補充ユニットが供給される
- **ZOC** — 敵の隣に踏み込むとそこで移動終了。戦線が意味を持つ
- **地形** — 移動コストと防御力が地形とユニット種別で変わる

を維持しつつ、次の3点を本作の独自性とする。

1. **索敵** — 視界外の敵は見えない。偵察と情報が戦術の一部になる
2. **現代・沿岸戦** — 舞台を宇宙から現代の地球へ移し、海上戦力と揚陸を追加する
3. **デバイスを問わず遊べる** — PC でもスマートフォンでも同じ体験で遊べる

### 原作からの主な変更点

| 観点 | 原作 | 本作 |
| --- | --- | --- |
| 舞台 | 月面・宇宙 | 現代地球（沿岸部を含む） |
| 地形 | 陸上中心 | 海洋・浅瀬・港・砂浜を追加 |
| ユニット | 陸・空中心 | 陸・空に加えて艦艇・潜水艦・揚陸を追加 |
| 索敵 | 全面可視 | 視界制（既定 ON） |
| 修理 | なし | 自軍施設に留まると回復 |
| 輸送 | 限定的 | 輸送ヘリ/揚陸艦による積載・揚陸を戦術要素として設計 |

## 3. アーキテクチャ

### 3.1 レイヤ構成

```
src/
├── core/          ゲームロジック（純粋・DOM 非依存・テスト対象の中心）
│   ├── hex.ts             ヘクス座標系と幾何計算
│   ├── types.ts           GameState / Unit / Tile などの型定義
│   ├── map.ts             マップ生成・タイル参照
│   ├── movement.ts        移動コスト・到達範囲・経路探索（ZOC 込み）
│   ├── vision.ts          視界計算・視点フィルタ（索敵）
│   ├── combat.ts          戦闘計算（サポート補正・反撃）
│   ├── facility.ts        施設の占領・増援・修理
│   ├── victory.ts         勝敗判定
│   ├── commands.ts        コマンド定義と検証
│   └── reducer.ts         reduce(state, command) => { state, events }
├── ai/            CPU 思考（core にのみ依存。視点フィルタ後の状態のみ受け取る）
├── render/        Canvas 描画（core を読むだけ。state を書き換えない）
│   ├── camera.ts          パン・ズーム・座標変換
│   └── layers/            地形 / 視界 / ハイライト / ユニット / エフェクト
├── input/         Pointer Events の抽象化（タップ・ドラッグ・ピンチ・ホバー）
├── ui/            画面遷移・パネル・レスポンシブレイアウト
├── data/          JSON ローダとスキーマ検証
├── editor/        マップエディタ（別エントリポイント）
└── main.ts

data/
├── units.json      ユニット性能表
├── terrain.json    地形定義
└── maps/*.json     マップデータ
```

**依存の向き**: `ui → input / render → core`、`ui → ai → core`。core は他を一切参照しない。
この分離により、core だけをヘッドレスで走らせて AI 同士の自動対戦テストが行える。

### 3.2 状態更新モデル（コマンドパターン）

すべてのプレイヤー操作・AI 操作を **Command** として表現し、単一の reducer で状態を更新する。

```ts
type Command =
  | { type: 'move';    unitId: UnitId; path: Hex[] }
  | { type: 'attack';  unitId: UnitId; targetId: UnitId }
  | { type: 'capture'; unitId: UnitId }
  | { type: 'load';    unitId: UnitId; carrierId: UnitId }
  | { type: 'unload';  carrierId: UnitId; unitId: UnitId; to: Hex }
  | { type: 'wait';    unitId: UnitId }
  | { type: 'endTurn' };

function reduce(state: GameState, cmd: Command): { state: GameState; events: GameEvent[] };
```

`events`（`unitMoved` / `unitSpotted` / `unitDamaged` / `unitDestroyed` / `facilityCaptured` …）は
描画・アニメーション・効果音のトリガとして使い、core は描画を知らない。

この設計により以下が自然に得られる。

- **アンドゥ**: 状態のスナップショット、またはコマンド列の再生
- **リプレイ**: 乱数なし・決定的なので「初期状態 + コマンド列」で完全再現
- **AI の先読み**: AI が仮想的に reduce を回して手を評価できる
- **セーブ/ロード**: GameState を JSON 化して localStorage へ
- **索敵の一貫性**: 完全情報の state は1つだけ持ち、UI・AI には視点フィルタを通した state を渡す

## 4. ゲームルール仕様

> 本章の数値はすべて JSON の定数として外に出し、コード変更なしで調整できるようにする。
> 「原作準拠」と書いた箇所も、実プレイでの検証を経て第10章のバランス調整フェーズで確定させる。

### 4.1 座標系

- **フラットトップ（左右に頂点、上下が平ら）の六角形**を、列ごとに縦方向へずらして配置。
  近隣は N / S / NE / SE / NW / SW の6方向。
- **保存形式**: マップ JSON は人間が読める `odd-q` オフセット座標（列・行の二次元配列）。
- **内部計算**: 読み込み直後に軸座標 (q, r) へ変換。距離・近隣・範囲計算はキューブ座標で行う。

```
軸座標への変換: q = col,  r = row - (col - (col & 1)) / 2
距離: (|dq| + |dq + dr| + |dr|) / 2
```

### 4.2 ターン進行

1. **ターン開始フェーズ**
   - 占領済み施設からの増援を出現させる
   - 自軍施設ヘクスに留まっているユニットを修理
   - 全ユニットの行動済みフラグをリセット
   - 視界を再計算
2. **操作フェーズ** — ユニットごとに「移動 → 攻撃 / 占領 / 積載 / 待機」を1回ずつ実行
3. **ターン終了** — 勝敗判定 → 相手プレイヤーへ

ユニットは1ターンに **移動1回 ＋ 行動1回**。攻撃・占領を行うと行動終了。
移動せずにその場で攻撃することも可能。

### 4.3 移動

- ユニットは **移動力（MP）** を持ち、進入するヘクスの移動コストを支払う
- コストは **地形 × 移動タイプ** の表で決まる（`terrain.json`）
- 移動タイプ: `foot`（歩兵） / `wheel`（装輪） / `track`（装軌） / `hover` / `air` / `ship`（水上） / `sub`（潜水）
- 進入不可の組み合わせはコスト `null`（例: 戦車と外洋、艦艇と平地）
- 経路探索は移動コスト付きダイクストラ。到達可能ヘクスをハイライト表示
- 味方ユニットのいるヘクスは**通過可能・停止不可**。敵ユニットのいるヘクスは通過不可
- **ZOC**: 敵ユニットに隣接するヘクスへ進入した時点で移動終了
  - 開始位置が既に ZOC 内の場合、そこから1ヘクスだけは移動できる（膠着を避けるため）
  - 航空ユニットは ZOC の影響を受けない（原作準拠）
  - ZOC を発生させるのは地上/海上ユニットのみ
  - **索敵 ON のため、ZOC は「見えている敵」に対してのみ経路計算に反映する**。
    見えていない敵の ZOC は次項の「遭遇による移動中断」で処理する
- **遭遇による移動中断**: 移動は1ヘクスずつ解決し、進入のたびに視界を再計算する。
  新たに敵を発見した時点でそこで移動を終了する（不意の遭遇の表現）

### 4.4 索敵と視界（既定 ON）

盤面は各プレイヤーから見て**3段階**の可視状態を持つ。

| 状態 | 表示 |
| --- | --- |
| 未探索 | 完全に黒。地形も施設も不明 |
| 探索済み・視界外 | 地形は記憶されて暗く表示。ユニットは表示しない。施設は最後に観測した所有者を表示 |
| 視界内 | 地形・ユニット・施設をすべて表示 |

#### 視界の判定

- 各ユニットは **視界値 `vision`** を持つ（歩兵2 / 偵察車4 / 戦車2 / 攻撃ヘリ4 / 戦闘機5 /
  駆逐艦4 / 潜水艦3 など。`units.json` で定義）
- 自軍ユニットから距離 `vision` 以内のヘクスが視界内
- **遮蔽**: 森林・市街地・山岳にいるユニットは、**隣接（距離1）でなければ発見できない**
  - ヘクスでのレイキャスト式 LOS は計算が重く、判定が直感に反しやすいため、
    「隠れられる地形」方式を採用する。ルールが単純でプレイヤーにもAIにも扱いやすい
  - 遮蔽地形そのもの（地形の存在）は視界内なら見える。隠れているのはユニットのみ
- **高所ボーナス**: 山岳・丘陵にいるユニットは視界 +1
- **航空ユニットは遮蔽を無視する**（上から見えるため）。偵察の主役になる
- **潜水艦**は、対潜能力を持つユニットに隣接された時のみ発見される（潜航状態）
- 自軍施設は常に視界を持つ（半径2）。占領した拠点周辺の安全が確保される

#### 実装方針

```ts
computeVisibility(state, playerId): VisibilitySet          // 視界内ヘクス集合
perspective(state, playerId): PlayerView                   // 敵ユニットを削った観測状態
```

- **UI も AI も必ず `perspective()` を通した状態のみを受け取る**。
  これにより「AI がカンニングしていないか」が型レベルで保証される
- 完全情報の `GameState` はセーブ・リプレイ・勝敗判定にのみ使う
- 探索済み地形の記憶は `PlayerMemory` としてプレイヤーごとに保持し、セーブ対象に含める
- ダメージ予測は視界内の敵にのみ表示する

### 4.5 戦闘（戦力10制・決定的）

各ユニットは **戦力 S**（初期値 10、0 で撃破）を持つ。戦力は攻撃力・被ダメージ量の両方に効く。
**乱数は使わない**ため、ダメージ予測を UI に常時表示でき、AI も正確に読める。

#### ダメージ計算

```
supportMul(n) = 1 + SUPPORT_STEP × min(n, SUPPORT_CAP)        // 既定: 0.15, 4

attackerMod = (S_attacker / 10) × supportMul(n_attacker)
defenderMod = DEF[defender.type]
              × terrainDefense[defender.tile][defender.type]
              × supportMul(n_defender)

damage = clamp( round( ATK[attacker.type][defender.armorClass]
                       × attackerMod / defenderMod ),
                0, S_defender )
```

- `ATK` は「攻撃側ユニット種別 × 防御側の耐性クラス（歩兵 / 装甲 / 艦艇 / 航空 / 潜水）」の表
- `DEF` はユニット固有の防御係数
- `terrainDefense` は地形の防御補正（市街・森・山でユニット種別ごとに変化）

#### サポート補正（本作の核）

- `n_attacker` = **防御側ユニットに隣接している攻撃側ユニットの数**（攻撃を実行したユニット自身は除く）
- `n_defender` = **攻撃側ユニットに隣接している防御側ユニットの数**（防御ユニット自身は除く）

つまり「敵を囲むほど強く殴れる／自分が囲まれているほど弱い攻撃になる」。
戦線を維持し、突出した敵を包囲する動きが最善手になる。

**サポート数は視界に関係なく実際の隣接ユニット数で計算する**（見えていない味方も支援に数える）。
ただし UI の予測表示は、プレイヤーが知り得る情報のみで計算した値を出す。

> ⚠️ 原作の正確な係数は資料により差異があるため、`SUPPORT_STEP` / `SUPPORT_CAP` は
> 調整パラメータとして扱い、プレイテストで決定する。

#### 反撃

- 攻撃解決後、防御側の戦力が 1 以上で、かつ攻撃側が**反撃可能な射程内**にいる場合、
  同じ式で反撃が発生する（このとき攻守の役割とサポート計算は入れ替わる）
- **間接攻撃ユニット**（自走砲・MLRS・ミサイル艦）は
  - 移動後に攻撃できない
  - 射程 2〜3 から攻撃し、反撃を受けない
  - 隣接した敵には攻撃できない（原作の間接砲と同じ扱い）
  - **索敵 ON のため、射程内でも「見えていない敵」は攻撃できない**。
    間接砲は前線ユニットの視界に依存する（＝偵察の価値が上がる）
- **対空ユニット**は航空機に大ダメージ、地上目標には低ダメージ
- **潜水艦**は対潜能力を持つユニットからのみ攻撃を受ける

### 4.6 施設・増援・修理（生産なし）

| 施設 | 効果 |
| --- | --- |
| 司令部（HQ） | 陣営の本拠地。占領されると敗北。地上ユニットの修理 |
| 工場 | 増援の供給元。**地上ユニットの修理** |
| 港 | 海上ユニットの増援出現点・**修理** |
| 飛行場 | 航空ユニットの増援出現点・**修理** |

#### 生産は存在しない

資源やお金を貯めてユニットを作る仕組みは**設けない**。ユニットの供給源は次の2つのみ。

1. マップの初期配置
2. マップ JSON に定義された、施設ごとの**増援キュー**

これにより、各マップの戦力配分は完全にマップ設計者がコントロールできる。
プレイヤーは「限られた戦力をいかに損耗させずに使うか」を考えることになり、
修理拠点の確保と部隊の引き際が重要な判断になる。

#### 占領

- 占領は**地上ユニット（`canCapture: true`）のみ**が実行できる。施設ヘクスに乗り `capture` を実行
- 占領は1ターンで完了（原作準拠。第13章の検討課題）

#### 増援

- 各施設はマップ JSON に「出現ユニット列（キュー）」と「出現間隔」を持つ
- 占領している陣営が、間隔ターンごとにキューの先頭を隣接する空きヘクスへ出現させる
- キューが尽きたらそれ以上は出ない
- 出現するユニットは戦力10。出現したターンは行動済み

#### 修理

- 自軍が所有する施設ヘクスに乗ったままターンを終えると、次のターン開始時に **戦力 +3**（上限10）
- 施設の種別と回復可能なユニットは上表のとおり（工場に艦艇は入れないので自然に分かれる）
- 修理のみで、弾薬・燃料といった補給の概念は導入しない

### 4.7 輸送・積載（海洋要素の中核）

- **輸送ヘリ / 輸送トラック / 装甲兵員輸送車 / 揚陸艦** は積載枠を持つ
- 積載可能なのは歩兵系ユニット（揚陸艦は車両も可）
- 積載中のユニットは行動できず、視界も持たない。輸送ユニットが撃破されると同時に失われる
- **揚陸**: 揚陸艦は「砂浜」「港」に隣接した浅瀬から、地上ユニットを陸上ヘクスへ降ろせる
- 降ろされたユニットはそのターン行動済み（強襲上陸を強すぎなくするため）

索敵 ON との相乗効果で、「敵に見つからないルートで揚陸部隊を回し、手薄な工場を奪う」
「対艦ミサイルで揚陸部隊を沈める前に発見できるか」という読み合いが生まれる。

### 4.8 勝敗条件

以下のいずれかで決着。マップ JSON でどれを有効にするか指定する。

1. 敵ユニットの全滅
2. 敵司令部の占領
3. 規定ターン経過時点での判定（残存戦力・占領施設数で比較）

判定は完全情報の `GameState` に対して行う（索敵の影響を受けない）。

## 5. データ定義

### 5.1 ユニット（`data/units.json`）

原作級の規模を目指し、**現代設定 + 海上戦力**で全21種を計画する。

## 6. AI 設計

`ai/types.ts` にインターフェースを切り、実装を差し替えられるようにする。
**AI は `perspective()` で視点フィルタされた状態のみを受け取る**ため、
人間と同じ情報量で戦う（カンニングしない）。

```ts
interface AiPlayer {
  planTurn(view: PlayerView, playerId: PlayerId): Command[];
}
```

### v1（MVP 用・貪欲）

各ユニットについて、実行可能な行動を列挙し、単純なスコアで最良手を選ぶ。

1. 攻撃可能な（＝見えている）敵がいれば、`与ダメージ − 想定反撃ダメージ` が最大の攻撃を選ぶ
2. 占領可能な施設に乗れるなら占領
3. 戦力が半分以下なら自軍施設へ後退して修理
4. どれも無ければ、既知の敵または未占領施設へ前進。敵が1体も見えていない場合は
   **未探索領域へ偵察ユニットを向かわせる**

索敵があるため、AI には「敵が見えないときに何をするか」が必須になる。
未探索ヘクスへの誘導を v1 から入れておく。

### v2（評価関数型）

盤面評価関数を定義し、1ターン分の行動順を貪欲＋局所探索で最適化する。

```
score = Σ(自軍ユニット戦力 × 種別価値) − Σ(既知の敵戦力 × 種別価値)
      + W_facility × 占領施設数の差
      + W_hq       × 敵HQへの距離の逆数
      + W_support  × サポート優位（自軍が敵を囲めている数 − その逆）
      + W_terrain  × 各ユニットの地形防御ボーナス
      + W_vision   × 視界に収めているヘクス数（索敵の価値）
      − W_risk     × 未探索領域に隣接している自軍ユニット数（伏兵リスク）
```

- 行動順序（誰から動かすか）が結果を大きく変えるため、
  複数の順序をサンプリングして最良のものを採る
- 相手の反撃は1手先まで読む（`reduce` を仮想実行してシミュレート）
- 見えていない敵は「最後に観測した位置から移動力ぶん広がった存在確率」として概算し、
  危険地帯を避ける
- 難易度は、評価関数の重み・探索の広さ・「あえて最善を選ばない確率」で3段階を用意

### 自己対戦テスト

ヘッドレスで AI 同士を数百戦させ、
- 例外・無限ループ・不正コマンド・膠着（互いに見つけられず進まない）の検出
- マップごとの先手勝率（バランス指標）
を CI とは別のスクリプトで測定する。

## 7. UI / UX（マルチデバイス対応）

**PC・タブレット・スマートフォンのいずれでも同じゲームが快適に遊べること**を要件とする。
これは後付けが非常に高くつくため、Phase 2 の時点で入力抽象化とカメラを作り込む。

### 7.1 入力の抽象化

- **Pointer Events** に統一し、マウス・タッチ・ペンを1つのコードパスで処理する
- ジェスチャ層で `tap` / `longPress` / `drag` / `pinch` / `hover`（対応デバイスのみ）を解釈
- **ホバー前提の設計を禁止する**。ホバーでしか得られない情報を作らない

### 7.2 操作

| 操作 | PC | タッチ |
| --- | --- | --- |
| ユニット選択 | クリック | タップ |
| 移動先指定 | クリック（経路プレビュー→確定） | タップ（経路プレビュー→確定ボタン） |
| ダメージ予測 | 敵にホバーで即表示 | 敵をタップで表示 → もう一度タップで攻撃実行 |
| 情報表示 | ホバー | 長押し |
| カメラ移動 | ドラッグ / 端でのスクロール / 方向キー | 1本指ドラッグ |
| ズーム | ホイール / `+` `-` | ピンチ / ダブルタップ |
| 選択解除 | 右クリック / Esc | 空きヘクスをタップ / 戻るボタン |
| ターン終了 | Enter / ボタン | ボタン（未行動ユニットがあれば確認） |
| 未行動ユニット送り | Space | 画面上のボタン |
| アンドゥ | `U` / ボタン | ボタン |

- **移動・攻撃は必ず「プレビュー → 確定」の2段階**にする。誤タップの被害を防ぐ
- アンドゥ（自ターン内の自分の行動）は常に用意する

### 7.3 レスポンシブレイアウト

| 画面 | レイアウト |
| --- | --- |
| 横長（PC・タブレット横） | マップ中央 + 情報パネル右 + 操作バー下 |
| 縦長（スマートフォン） | マップを画面の大半に配置 + 下部にボトムシート（選択中ユニット情報・行動ボタン）。詳細は上スワイプで展開 |

- ヘクスの表示サイズは画面幅に応じて可変。初期ズームは「マップ全体が入る」か
  「タップ可能な最小サイズを確保」のうち大きい方
- タップ対象は 44 CSS px 以上を確保。確保できない縮尺ではタップ時に自動でズームインする
- セーフエリア（ノッチ・ホームバー）に対応
- 画面回転・リサイズで再レイアウトし、カメラの注視点は維持する

### 7.4 描画

- Canvas をレイヤ分割: 地形（オフスクリーンにキャッシュ）→ 視界（未探索/視界外のマスク）→
  グリッド → ハイライト → ユニット → エフェクト → HUD
- `devicePixelRatio` に対応して高解像度端末でもぼやけないようにする
- 描画は**カメラの可視範囲のヘクスのみ**。マップが大きくてもモバイルで性能が落ちない
- アニメーション（移動・被弾・撃破・敵発見）は `events` を消費するキューで処理し、
  再生中は入力をブロックする。**速度設定とスキップを必ず用意する**
- 低スペック端末向けに「エフェクト簡略化」設定を持つ
- ユニット表現は Phase 2 までは色付きヘクス＋記号のプレースホルダ。
  Phase 8 以降で自作スプライトに差し替え

### 7.5 索敵の見せ方

索敵は「何が起きたか分からない」状態を生みやすいので、表示を厚くする。

- 未探索は黒、探索済み・視界外は暗いオーバーレイで明確に区別する
- **敵を新たに発見したとき**は、そのヘクスを強調しカメラを寄せる（スキップ可）
- 敵ターン中に自軍が攻撃された場合、その位置へカメラを移動して結果を示す
- 選択中ユニットの視界範囲を任意で常時表示できるトグルを置く
- サポート数の可視化（攻撃時に支援している味方ヘクスを枠線で示す）は学習コストを
  大きく下げるため優先度を高くする

## 10. テスト戦略

| 種別 | 対象 | 方針 |
| --- | --- | --- |
| 単体テスト | `core/` 全体 | ヘクス幾何、移動コスト、ZOC、視界計算、戦闘計算、占領、増援、修理、勝敗判定 |

| 実機確認 | UI | Phase 2 / 5 / 7 で、スマートフォン実機（縦・横）とタブレットで操作確認 |

## 13. 検討課題（レビューで決めたい点）

実装前に方針を確定したい項目。**太字が本書としての推奨案**。

1. **占領の所要ターン** — **1ターンで完了（原作準拠、テンポ重視）** / 2ターン制（防衛の余地が生まれる）
2. **サポート補正の係数** — 推奨は `+15% × min(隣接数, 4)`（最大 +60%）。
   原作の体感に近づくよう Phase 5 のプレイテストで調整
3. **視界の遮蔽方式** — **「森林・市街地・山岳のユニットは隣接しないと発見できない」方式**を推奨。
   レイキャスト式 LOS は計算コストと直感性の両面で不利
4. **修理速度** — **+3/ターン**（4ターンで全快）を推奨。速すぎると膠着し、遅すぎると死に要素になる
5. **AI に索敵のハンデを与えるか** — **難易度「難」でも視点フィルタを守る（カンニングさせない）**。
   強さは思考の質で出す
6. **航空ユニットの燃料** — **なし**（原作準拠）。無制限に飛べる代わりに、対空ユニットを
   強めに設定して抑止する
7. **マップサイズ** — 初期マップは 20×14 前後。スマホ縦画面では全体が入らないため、
   ミニマップまたは全体表示ズームを Phase 7 で用意する
8. **陣営数** — **2陣営固定**。3陣営以上はデータ構造上は許容するが UI/AI では対応しない
9. **増援の見え方** — 敵陣の増援は視界外なら当然見えない。**「敵工場から増援が出た」ことすら
   通知しない**（索敵の緊張感を優先）を推奨

## 14. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 数値バランスが煮詰まらない | ゲームとして面白くならない | 全定数を JSON 化。Phase 5 でプレイテスト期間を明示的に確保。自己対戦で定量評価 |
| 索敵で AI が極端に弱くなる | 1人用ゲームとして成立しない | v1 から「未探索領域への偵察」を組み込む。v2 で敵存在確率の推定を入れる。自己対戦で膠着率を監視 |
| 索敵で「何も起きないターン」が増える | 中盤が退屈になる | 偵察ユニットの視界を厚くし、マップを広くしすぎない。敵発見時の演出を強くする |
| サポート/ZOC がプレイヤーに伝わらない | 戦術が理解されず作業ゲーに見える | サポート数の可視化とダメージ予測を Phase 5 の必須項目に含める |
| モバイルの操作性・性能が確保できない | 「デバイスを問わず」の要件を満たせない | Phase 2 で実機確認を DoD に入れる。可視範囲のみ描画。Phase 7 で最適化を独立したフェーズとして確保 |
| スマホ画面にマップが収まらない | 全体戦況が把握できない | ミニマップ／全体ズーム／ボトムシート UI で対処（Phase 7） |
| AI ターンが長い / 見ていて退屈 | 体験の質が落ちる | 探索の深さに上限を設ける。アニメーション速度設定とスキップを必ず用意 |
| ユニット21種の作り込みで停滞 | MVP が遠のく | Phase 5 までは 8種程度で進め、システム確定後に JSON で追加する |
| 海洋要素が陸戦と噛み合わない | 追加要素が死ぬ | Phase 10 で沿岸マップを専用設計し、「海路が最短の目標」を必ず配置する |
| 素材制作がボトルネック | 見た目が最後まで仮のまま | Phase 8 まではプレースホルダ図形で進行。ロジック完成を優先 |
